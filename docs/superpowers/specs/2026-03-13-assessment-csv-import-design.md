# Assessment CSV Bulk Import - Design Spec

## Context

Seven historical CSV files (nine logical sections -- one file contains three formats) in `assesments-to-import/` contain player assessment data from March 2024 through January 2025. These need a one-time import into the existing `player_assessments` table. Future assessments will be entered through the system UI.

The challenge: files use at least 4 different formats (standard columnar, reordered columnar, vertical card with pairs, vertical labeled blocks), with inconsistent column ordering, mixed units (meters vs cm), typos in names, and one file (November) containing 3 different formats within itself.

## Approach: Two-Phase Import with Mapping File

**Phase 1 (Extract):** Parse all CSVs, fuzzy-match names to Supabase profiles, output a single `mapping.csv` for human review.

**Phase 2 (Import):** Read the reviewed `mapping.csv`, insert into `player_assessments`.

This gives full visibility into every value before it hits the database and provides an audit trail.

## Architecture

### Files

```
scripts/
  import-utils.ts           # Shared utilities (extracted from existing import-assessments.ts)
  extract-assessments.ts     # Phase 1: parse CSVs -> mapping.csv
  import-from-mapping.ts     # Phase 2: mapping.csv -> Supabase
assesments-to-import/
  mapping.csv                # Generated by Phase 1, reviewed by human
```

### Phase 1: Extract (`scripts/extract-assessments.ts`)

Usage:
```bash
npx tsx scripts/extract-assessments.ts [--output assesments-to-import/mapping.csv]
```

Processes all 7 CSV files (9 logical sections) using format-specific parsers, fuzzy-matches names to Supabase profiles, writes `mapping.csv`.

### Phase 2: Import (`scripts/import-from-mapping.ts`)

Usage:
```bash
npx tsx scripts/import-from-mapping.ts assesments-to-import/mapping.csv --dry-run
npx tsx scripts/import-from-mapping.ts assesments-to-import/mapping.csv
```

Reads reviewed `mapping.csv`, skips rows with empty `profile_id`, inserts into `player_assessments` using the Supabase service role key (bypasses RLS). Idempotent: checks for existing assessment on same user+date, filtering `deleted_at IS NULL` to align with the partial unique index.

### Shared Utilities (`scripts/import-utils.ts`)

Extracted from existing `scripts/import-assessments.ts`:
- `.env.local` loader
- Supabase admin client factory
- `extractNumber()` - strip Hebrew text, handle comma decimals, filter junk
- `normalizeToCm()` - values < 10 assumed meters
- `parseSingleLegJump()` - extract ימין/שמאל with nearest-number association
- `parseKaiserJumpHeight()` / `parseKaiserKickPower()` - split height vs power
- `normalizeName()` / `findProfileMatch()` - three-tier name matching
- CSV line parser (handles quoted fields)

## Parsers

### 1. `parseStandardColumnar`

**Used by:** July, August, October, March-April

Fixed column positions:
- Col 0: name
- Col 1: kaiser/height
- Col 2: 2-leg jump distance
- Col 3: single-leg jump (free text with ימין/שמאל)
- Col 4: sprint 5m
- Col 5: sprint 10m
- Col 10: blaze spot (חשיבה מהירה)

Filters out rows where name is empty, header-like ("שם השחקן", "שם שחקן", "שם"), or metadata ("תשאירו", "עמודה").

### 2. `parseReorderedColumnar`

**Used by:** November lines 1-95, November sub-table lines 271-275

Maps columns by header keywords rather than position:

- "ניתור רגל ימין" / "קפיצה למרחק רגל ימין" -> jump_right_leg
- "ניתור רגל שמאל" / "שאמאל" / "קפיצה למרחק רגל שמאל" -> jump_left_leg
- "בלייז ספוט" / "זריזות.*פודים" -> blaze_spot_time
- "ניתור 2 רגליים למרחק" / "קפיצה למרחק 2 רגליים" -> jump_2leg_distance
- "מהירות.*5" / "ספרינט 5" -> sprint_5m
- "מהירות.*10" / "ספרינט 10" -> sprint_10m
- "ניתור.*לגובה" -> jump_2leg_height (apply kaiser/height splitting logic: large number = height, % marker = kaiser)

Sub-table special case (lines 271-275): has two height columns (`ניתור לגובה 3.5` and `ניתור לגובה 5`). Use `ניתור לגובה 5` for `jump_2leg_height`. Drop `ניתור לגובה 3.5`.

Dropped columns: diagonal agility (10m, 5m), agility pods.

### 3. `parseVerticalCard`

**Used by:** November lines 281-520

Structure:
```
player name
(optional blank lines)
"5 מ - 5.32, 5.40"
"10 מ - 8.95, 8.73"
"קפיצה שתי רגליים - 1.80, 1.85"
"שמאל - 1.55, 1.45"
"ימין - 1.35, 1.43"
(blank lines separate players)
```

Each line has two attempts. Take the **better** value (lower for sprints, higher for jumps).

Detection: lines that start with a Hebrew name followed by measurement lines matching `"X מ - N, N"` pattern.

Text notes (e.g., "קרסוליים קשיחות, לא הכי יציב") are stored in `notes` if present.

Parser must flush the last player record at EOF, not only on blank-line delimiter.

### 4. `parseVerticalLabeled`

**Used by:** Kawkab November

Structure:
```
,,,,,,,,,,אדהם,חודש נובמבר
,,,,,,,,,,5 מטר: 1.03,
,,,,,,,,,,10 מטר: 1.88,
,,,,,,,,,,קפיצה שתי רגליים: 2.17,
,,,,,,,,,,רגל ימין: 1.90,
,,,,,,,,,,רגל שמאל: 2.05,
,,,,,,,,,,זריזות: 5.36,
```

Data is in column 10 (0-indexed). Player name line has a name without a colon. Measurement lines have `label: value` format.

Label mapping:
- "5 מטר" -> sprint_5m
- "10 מטר" -> sprint_10m
- "קפיצה שתי רגליים" -> jump_2leg_distance
- "רגל ימין" -> jump_right_leg
- "רגל שמאל" -> jump_left_leg
- "זריזות" -> dropped (diagonal agility)

## Data Normalization Rules

### Numeric Extraction
- Commas as decimal separators: `"1,11"` -> `1.11`
- Strip Hebrew text, `%`, `#`, stars; keep digits/dots/minus
- `"?"`, `"??"`, `"0"`, empty -> `null`

### Sprints (seconds)

- Values > 30: divide by 100 (e.g., `240` -> `2.40`)
- Expected range: 0.8 - 3.0s. Flag outliers as warnings.
- Sprint values are never passed through `normalizeToCm()` -- only jump distances use that conversion.

### Jumps (cm)
- Values < 10: multiply by 100 (meters to cm)
- Single-leg: extract ימין/שמאל keywords, associate nearest number
- `"רגל ימין ושמאל 138"` -> both = 138

### Kaiser/Height Column

Column contains mixed data like `"188 7%"`, `"204 7%"`, `"83 3%"`. Parse both values:

- Large number (> 20) -> `jump_2leg_height` (cm)
- Number before `%` marker -> `kick_power_kaiser` (e.g., `7%` -> `7`)
- Same splitting logic applies to the `ניתור.*לגובה` column in the reordered columnar format

### Blaze Spot
- Integer count of hits
- `"38 חצי דקה"` -> `38`

### Vertical Card Pairs
- Two attempts per line, take the better value (lower for sprints, higher for jumps)

### Coordination
- `1` -> `deficient`, `2-3` -> `basic`, `4-5` -> `advanced`

### Dropped Fields

- `sprint_20m` -- no historical CSV file contains 20m sprint data (always null)
- Diagonal agility sprints (5m/10m columns)
- Flexibility, stability, running technique (all zeros in every file)
- Agility pods from sub-table
- `ניתור לגובה 3.5` from sub-table (only `ניתור לגובה 5` used)
- "זריזות" from Kawkab file

## Name Matching

### Three-Tier Strategy

1. **Exact** (`match_confidence=exact`): normalized names match exactly
2. **Partial** (`match_confidence=partial`): one name contains the other
3. **Token overlap** (`match_confidence=token`): >= 50% token overlap (tokens > 1 char)

### Normalization
- Trim, collapse whitespace
- Strip `'"():-.` and Unicode RTL/LTR marks
- Lowercase

### Known Edge Cases
- Typos in CSV: "שמאךל", "אורי ארדנולדס", "ינין"
- First-name only: "איתי", "דורון", "אדהם" -- may match multiple profiles
- Nicknames: "זוזו", "חמודי" -- unlikely to match
- Duplicates: "אדם משיח" x2, "רוי חמו" x2 in November -- both mapped, user decides

### Mapping CSV Output

```csv
source_file,csv_name,matched_profile_name,profile_id,assessment_date,match_confidence,sprint_5m,sprint_10m,sprint_20m,jump_2leg_distance,jump_right_leg,jump_left_leg,jump_2leg_height,kick_power_kaiser,blaze_spot_time,coordination,warnings
```

## Review Workflow

1. Run `npx tsx scripts/extract-assessments.ts`
2. Open `assesments-to-import/mapping.csv` in a spreadsheet
3. Sort by `match_confidence` -- fix `none` rows by filling in `profile_id` from Supabase
4. Verify `token` matches are correct
5. Delete rows to skip
6. Run `npx tsx scripts/import-from-mapping.ts assesments-to-import/mapping.csv --dry-run`
7. Review dry-run report
8. Run without `--dry-run` for live import

## Non-Goals

- No new database columns or migrations
- No UI changes
- No reusable import pipeline (one-time use)
- No automated handling of ambiguous first-name-only matches (human decides)
